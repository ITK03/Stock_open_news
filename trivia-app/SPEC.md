# ZATSU 仕様

会話に散らばった決定をここに集約する。**このファイルが仕様の正。**

初期に貼られた Gemini 生成プロンプトは仕様ではない。あの文面には意図と逆の項目が
混ざっていたため（末尾「上書きされた項目」参照）、以後は参照しない。

---

## 1. コンセプト

- ターゲット: 短時間で刺激（ドパミン）を求める若年層。
- 通常時は視覚的ノイズをゼロにし、**アクションを起こした時だけ**フルカラーの
  派手なエフェクトと振動で快感を与える。
- UI は極限までシンプル。背景は黒（または白）、文字は反転色のみ。
  **グレーや装飾は一切使わない。**

### 色の意味づけ（世界観の根幹）

| 色 | 意味 | 使う場面 |
| --- | --- | --- |
| 無彩色2色（黒/白） | 通常状態 | 常時。ここにノイズを足さない |
| **ネオン** | **報酬** | リアクション（ポジティブ）のみ |
| **無彩色の破壊表現** | **破棄** | BAD のみ。ネオンを使わない |

BAD に報酬の色（ネオン）を与えない。爽快感は「破壊の手触り」で出し、
報酬の通貨（ネオン）は渡さない。これが混ざると BAD が快感目的で連打される。

## 2. 画面

### フィード画面（主画面）

- 最上部と最下部にバナー広告。セーフエリア内に置き、本文と絶対に被らないよう
  パディングを取る。
- 画面中央は雑学テキストのみ。**ボタン類は一切置かない（完全ボタンレス）。**
- オチは極太・特大フォントで画面幅いっぱい。太さは OS 依存にしない。

### 詳細画面（左スワイプで開く）

- その雑学の**詳細説明**を表示する。
- **この画面でもリアクション（ダブルタップ）ができる。** 回数はフィード画面と共通で、
  合計8回まで。フィードで3回叩いてから開いたら、詳細画面では残り5回。
- **ブックマークと共有はこの画面に置く。**
- ここは**ボタンレスの例外**。「完全ボタンレス」はフィード画面に限る。

## 3. 操作

### 確定

| ジェスチャー | 動作 |
| --- | --- |
| 上スワイプ | 次の雑学へ。**遅延ゼロ**で即座に切り替える |
| ダブルタップ | リアクション（ポジティブ評価）。**1件につき最大8回**。回数ごとに演出と振動が増幅 |
| 長押し | **BAD。** 雑学が破壊される演出 → 即座に次へ送る |
| 左スワイプ | **詳細画面を開く** |
| 単純タップ | **恒久的に未割り当て。** 割り当てるとダブルタップ判定の待ち時間（約220ms）が必ず入り、リアクションの即応性が死ぬ。空けておくのは仕様 |
| 下スワイプ | 未割り当て |

### リアクション8回到達時（自動送り）

1. 8回目の演出を見せるため **約300ms 待つ**。即送りすると一番大きい快感を自分で潰す。
2. 次の雑学へ送る。**切り替わったことが明確に分かる演出**を入れる
   （送り出しアニメは入れない方針なので、入場側で明示する）。
3. 送った直後 **約300ms は評価系（ダブルタップ・長押し）を受け付けない。**
   連打の余りが次の雑学に流れ込むのを防ぐため。
   **スワイプは止めない**（止めると壊れて見える）。

8回目のタップから実質600ms 評価が効かない。当初案の「0.5秒程度」とほぼ同じ体感。

### BAD の演出方針

- 雑学が**物理的に破壊される**表現。文字が砕けて崩れ落ちる方向。
- **ネオンは使わない**（報酬の通貨を渡さない）。無彩色で完結させる。
- Haptic は達成パターンではなく、重い一撃 + 崩落の微振動。
- 破壊しきったら**即座に次へ送る**。嫌だと言われたものを見せ続けない。
- **演出は段階的に育てない。** リアクションは8段階で育つが BAD は常に同じ。
  育つ演出は繰り返したくなり、育たない演出は飽きる。この非対称が
  「BADを娯楽として連打する」を構造的に抑える。

## 4. データ

**雑学本体はサーバー、ユーザーの行動はローカル。** この線引きは動かさない。

| データ | 置き場所 | 理由 |
| --- | --- | --- |
| 雑学の本文（文字のみ） | **サーバー** | 100万件規模。端末に置かない |
| 雑学の詳細説明 | **サーバー** | 本文より重い。本文とは別に取る（下記） |
| 各雑学へのリアクション回数（0〜8） | **端末ローカル** | ユーザー個人のデータ |
| BAD フラグ | **端末ローカル** | 同上 |
| ブックマーク | **端末ローカル** | 同上 |

- **想定件数は100万件。** 設計はこの規模を前提にする。
- **サーバーの負荷はできるだけ軽くする。**
- **リアクション上限は永久保存。** 件数を大幅に増やすので、叩ける総量が実質尽きない。

### 詳細説明の配信

本文シャードに詳細を同梱**しない**。詳細は本文よりずっと重く、同梱するとシャードが
数倍に膨らんで「1リクエストで500件」の軽さが崩れる。詳細を読むのは左スワイプされた
一部の雑学だけなので、**個別ファイルで取得する**のが最も軽い。

## 5. 通信は必須

**オフラインで起動して広告を出さずに雑学だけ遊べてしまう状態を許さない。**
これが通信必須の理由であり、単なる技術的都合ではない。

1. 雑学を端末に永続化しない。
2. 通信が切れている間は遊べない（手持ちが残っていても止める）。
3. アプリ内にフォールバックの雑学データを持たない。

## 6. 広告

- 上下バナーは常時表示。
- インタースティシャル（全面広告）は**上スワイプ30回ごと**に1回。
- 現段階は実SDK未導入で、視覚的にわかるプレースホルダー。

## 7. 計測とプロフィール

**運営の手間を増やさない形で評価を吸収する。**

- 任意でプロフィール（性別・年代など）を入力させ、PR の精度を上げる。
- 「どの雑学がどの世代・性別に人気か」を集計したい。
- データが重くなりすぎないよう軽く扱う。

### 軽く保つための方針

- **生ログを送らない。** 端末側で集計し、セッション終了時に1回だけ小さく送る。
- 送るのは前回送信からの**差分**のみ（雑学id → 最終リアクション段階、BAD、閲覧）。
- プロフィールは**年代・性別のバケット**だけ持つ。生年月日は持たない
  （持つと個人情報の管理義務が跳ね上がる）。

## 上書きされた項目（Gemini プロンプトからの変更）

混乱の元なので明示しておく。左が元の文面、右が実際の仕様。

| Gemini プロンプトの記述 | 実際の仕様 |
| --- | --- |
| サーバー通信は行わず、ローカル JSON を持たせる | **逆。通信必須。**雑学はサーバー配信 |
| モックデータ50件程度 | **100万件想定** |
| インタースティシャルは15回ごと | **30回ごと** |
| 長押し = お気に入り保存 | **長押し = BAD。**「保存」でも perfect でもない |
| リアクション最大5回・送りは手動 | **最大8回・8回到達で自動送り** |
| （フォントの指定なし → OS 任せ） | **フォント同梱で iOS/Android の見た目を揃える** |

一時的に「長押し = perfect 評価」「左スワイプ = BAD」という案があったが、
どちらも廃止。現在の割り当ては上の表が正。

## 未確定

### 演出
- **リアクションの演出段階数。** 上限は8回だが、現在の実装は5段階しかない。
  6〜8回目に増幅の余地が無く、climax の直前に「叩いても何も変わらない3回」ができる。
  8段階に拡張するか、6回目以降を MAX 演出の連続爆発にするか。

### 詳細画面
- **戻り方**（右スワイプ / 下スワイプ / どちらも）。
- **詳細画面で8回目に到達したらどうなるか。** 詳細を閉じてフィードの次へ送るのか、
  詳細に留まるのか。
- **詳細画面で長押し（BAD）はできるのか。**
- **詳細画面にもバナー広告を出すのか。**
- **詳細説明が長文で縦スクロールする場合**、スクロールと上下スワイプが競合する。
  詳細画面のジェスチャー割り当てを別に決める必要がある。
- 詳細説明のデータをどう持つか（文字数の上限、本文と同じ生成パイプラインに乗せるか）。

### 計測
- **集計の受け先。** ここまでの構成は静的ファイル配信のみ（GET だけ）だったが、
  評価の送信は書き込みなので**初めて受け口が必要になる**。
  既製の分析SaaS に投げるのが運営負担は最小。自前なら Cloudflare Workers 等。
- **対象年齢の下限。** ここが収益モデルに直結する（下記）。

### 収益モデルとの衝突（要判断・重要）
ターゲットが若年層で、かつ年齢・性別を広告ターゲティングに使う場合、
**児童向けアプリと判定されるとパーソナライズ広告が禁止**される
（Google Play ファミリー ポリシー / COPPA / GDPR-K）。
「PR の精度を上げる」という狙いが根本から成立しなくなるため、
**対象年齢の下限を先に決める**必要がある。あわせてプライバシーポリシー、
App Store の App Privacy と Google Play の Data safety 申告が必須。

### 配信ホスティング
- GitHub Pages は容量と商用前提の観点で本番不可。Cloudflare R2 等を推奨。
  配信側は静的ファイルのみで完結させてあるので `src/config.ts` の差し替えで移れる。
