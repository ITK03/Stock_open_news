# ZATSU 仕様

会話に散らばった決定をここに集約する。**このファイルが仕様の正。**

初期に貼られた Gemini 生成プロンプトは仕様ではない。あの文面には意図と逆の項目が
混ざっていたため（末尾「上書きされた項目」参照）、以後は参照しない。

---

## 0. スワイプの向きの表記

取り違えの元なので、このファイルでは**必ず指の動く向き**で書く。

| 表記 | 指の動き | 文書の中では |
| --- | --- | --- |
| **上スワイプ** | 指を上へ払う | 文書を下（末尾方向）へ送る |
| **下スワイプ** | 指を下へ払う | 文書を上（先頭方向）へ戻す |

つまり「上スワイプ＝次」「下スワイプ＝前」で、詳細画面のスクロールと同じ向きに揃う。

## 1. コンセプト

- ターゲット: 短時間で刺激（ドパミン）を求める若年層。
- 通常時は視覚的ノイズをゼロにし、**アクションを起こした時だけ**フルカラーの
  派手なエフェクトと振動で快感を与える。
- UI は極限までシンプル。背景は黒（または白）、文字は反転色のみ。
  **グレーや装飾は一切使わない。**

### 色の意味づけ（世界観の根幹）

| 色 | 意味 | 使う場面 |
| --- | --- | --- |
| 無彩色2色（黒/白） | 通常状態 | 常時。ここにノイズを足さない |
| **ネオン** | **報酬** | リアクション（ポジティブ）のみ |
| **無彩色の破壊表現** | **破棄** | BAD のみ。ネオンを使わない |

BAD に報酬の色（ネオン）を与えない。爽快感は「破壊の手触り」で出し、
報酬の通貨（ネオン）は渡さない。これが混ざると BAD が快感目的で連打される。

## 2. 画面

### フィード画面（主画面）

- 最上部と最下部にバナー広告。セーフエリア内に置き、本文と絶対に被らないよう
  パディングを取る。
- 画面中央は雑学テキストのみ。**ボタン類は一切置かない（完全ボタンレス）。**
- オチは極太・特大フォントで画面幅いっぱい。太さは OS 依存にしない。

### 詳細画面（左スワイプで開く）

- その雑学の**詳細説明**を表示する。
- **リアクション（タップ）ができる。** 回数はフィード画面と共通で合計8回。
  フィードで3回叩いてから開いたら、詳細画面では残り5回。
- **BAD（長押し）もできる。**
- **バナー広告も出す**（上下、フィードと同じ）。
- **ブックマークと共有はこの画面に置く。** ここは**ボタンレスの例外**。
  「完全ボタンレス」はフィード画面に限る。
- **右スワイプで閉じる。**

## 3. 操作

### フィード画面

| ジェスチャー | 動作 |
| --- | --- |
| **タップ** | リアクション（ポジティブ評価）。**1件につき最大8回**。回数ごとに演出と振動が増幅 |
| 長押し | **BAD。** 雑学が破壊される演出 → 即座に次へ送る |
| 上スワイプ | **次**の雑学へ。**遅延ゼロ**で即座に切り替える |
| 下スワイプ | **前**の雑学へ戻る |
| 左スワイプ | 詳細画面を開く |

リアクションは**単一タップ**。ダブルタップにしない。理由は2つあり、どちらも
コンセプトの根幹に効く。

1. **ダブルタップは2回目を待つ間の遅延（約200ms）が必ず入る。**「遅延ゼロ」を
   掲げているのにリアクションだけ待たされるのは矛盾する。単一タップなら待ち時間ゼロ。
2. 上限8回に達するまでのコストが半分（8タップ vs 16タップ）。連打の快感は
   単一タップでしか出ない。

実装上の境界: **タップの maxDuration を長押しの minDuration より短くする**
（例 タップ 300ms / 長押し 350ms）。押しっぱなしがタップにも長押しにも
判定される曖昧な帯を作らない。

### 詳細画面

| ジェスチャー | 動作 |
| --- | --- |
| タップ | リアクション（フィードと共通カウント、合計8回まで） |
| 長押し | BAD |
| 右スワイプ | 詳細を閉じる |
| 上スワイプ | 本文をスクロール。**最下部に達していたら次の雑学へ** |
| 下スワイプ | 本文をスクロール。**最上部に達していたら前の雑学へ** |

スクロール端に達している時だけ、スワイプが雑学の移動に変わる（オーバースクロール）。

- 開いた直後は最上部なので、下スワイプで即座に前の雑学へ行ける。
- 少しでもスクロールしたら、最上部まで戻さないと前の雑学へは行けない。
- 本文が画面に収まりきってスクロール不要な場合は、両方向とも即座に移動になる。

### リアクション8回到達時（自動送り）

1. 8回目の演出を見せるため **約300ms 待つ**。即送りすると一番大きい快感を自分で潰す。
2. 次の雑学へ送る。**切り替わったことが明確に分かる演出**を入れる
   （送り出しアニメは入れない方針なので、入場側で明示する）。
3. 送った直後 **約300ms は評価系（タップ・長押し）を受け付けない。**
   連打の余りが次の雑学に流れ込むのを防ぐため。
   **スワイプは止めない**（止めると壊れて見える）。

**詳細画面で8回目に到達した場合も同じように送る。** その際は詳細を閉じて
フィードに戻り、次の雑学を表示する。

### リアクションの演出段階

上限は8回だが、演出の段階は5つ。**6回目以降は MAX 演出が毎回爆発する。**

| 回数 | 演出 |
| --- | --- |
| 1〜5回 | 段階的に増幅（粒の数・飛距離・振動が単調増加） |
| 6〜8回 | **MAX 演出を毎回撃つ**（増幅の余地が無い帯を「連続爆発」で埋める） |

段階を8つに割らずこうするのは、山なりに増幅 → 天井で爆発が連続 → 8回目で送り、
という起伏を作るため。単純に8段階へ薄く伸ばすと1回ごとの差が感じられなくなる。

### BAD の演出方針

- 雑学が**物理的に破壊される**表現。文字が砕けて崩れ落ちる方向。
- **ネオンは使わない**（報酬の通貨を渡さない）。無彩色で完結させる。
- Haptic は達成パターンではなく、重い一撃 + 崩落の微振動。
- 破壊しきったら**即座に次へ送る**。嫌だと言われたものを見せ続けない。
- **演出は段階的に育てない。** リアクションは育つが BAD は常に同じ。
  育つ演出は繰り返したくなり、育たない演出は飽きる。この非対称が
  「BADを娯楽として連打する」を構造的に抑える。

## 4. データ

**雑学本体はサーバー、ユーザーの行動はローカル。** この線引きは動かさない。

| データ | 置き場所 | 理由 |
| --- | --- | --- |
| 雑学の本文（文字のみ） | **サーバー** | 100万件規模。端末に置かない |
| 雑学の詳細説明 | **サーバー** | 本文より重い。本文とは別に取る（下記） |
| 各雑学へのリアクション回数（0〜8） | **端末ローカル** | ユーザー個人のデータ |
| BAD フラグ | **端末ローカル** | 同上 |
| ブックマーク | **端末ローカル** | 同上 |

**プロフィール（年代・性別）は収集しない。** 集計が「100万件 × 年代 × 性別」に
膨らんで軽さが崩れるため廃止した。副産物として、個人情報の管理義務・同意取得・
入力動線の設計がまとめて不要になる。

- **想定件数は100万件。** 設計はこの規模を前提にする。
- **サーバーの負荷はできるだけ軽くする。**
- **リアクション上限は永久保存。** 件数を大幅に増やすので、叩ける総量が実質尽きない。

### 詳細説明の配信

本文シャードに詳細を同梱**しない**。詳細は本文よりずっと重く、同梱するとシャードが
数倍に膨らんで「1リクエストで500件」の軽さが崩れる。詳細を読むのは左スワイプされた
一部の雑学だけなので、**個別ファイルで取得する**のが最も軽い。

### 「前へ戻る」のための履歴

下スワイプで前へ戻れるようにするには、表示済みの雑学をメモリに残す必要がある。
無制限に残すと長時間プレイでメモリが膨らむため、**直近 N 件だけ保持**する
（初期値50件程度、要調整）。それより前には戻れない。

## 5. 通信は必須

**オフラインで起動して広告を出さずに雑学だけ遊べてしまう状態を許さない。**
これが通信必須の理由であり、単なる技術的都合ではない。

1. 雑学を端末に永続化しない。
2. 通信が切れている間は遊べない（手持ちが残っていても止める）。
3. アプリ内にフォールバックの雑学データを持たない。

## 6. 広告

- 上下バナーは常時表示（フィード画面・詳細画面とも）。
- インタースティシャル（全面広告）は**上スワイプ30回ごと**に1回。
- 現段階は実SDK未導入で、視覚的にわかるプレースホルダー。
- **対象年齢は児童向けではない**として扱う。これによりパーソナライズ広告が使える
  （児童向け判定を受けると禁止され、プロフィールによる精度向上が成立しなくなる）。
  年齢の下限を設けたうえで、プライバシーポリシーと
  App Store の App Privacy / Google Play の Data safety 申告を用意すること。

## 7. 計測

**分析は自前で行う。外部の分析サービスは使わない。**
**プロフィール（年代・性別）は収集しない**（§4 参照）。したがって集計は
**雑学ごとの人気度のみ**で、デモグラ別の内訳は取らない。

### 軽く保つための方針

- **生ログを送らない。** 端末側で集計し、セッション終了時に1回だけ小さく送る。
- 送るのは前回送信からの**差分**のみ（雑学id → 最終リアクション段階 / BAD / 閲覧）。
- 受け口は**追記のみ**にする。受信時は生バッチをそのまま保存するだけで集計せず、
  **集計は後段のバッチ処理**で回す（このリポジトリが既に GitHub Actions で
  やっているのと同じ形）。受け口で集計しないので書き込み競合が起きず、
  スケールの心配がほぼ無くなる。
- **全件の精密な集計を持たない。** リアクションや BAD が付いた雑学だけを対象にする
  （100万件のうち大半は誰にも触られないので、実際の行数は激減する）。

### BAD は品質管理の主機構

100万件を機械生成する前提だと、全件の事実確認は現実的に不可能。
**BAD が「質の悪い雑学を淘汰する唯一の信号」になる。** 単なる評価機能ではなく
コンテンツ品質の根幹なので、集計対象から外さないこと。
BAD 率が高い雑学を配信から落とす運用を想定する。

## 上書きされた項目（Gemini プロンプトからの変更）

混乱の元なので明示しておく。左が元の文面、右が実際の仕様。

| Gemini プロンプトの記述 | 実際の仕様 |
| --- | --- |
| サーバー通信は行わず、ローカル JSON を持たせる | **逆。通信必須。**雑学はサーバー配信 |
| モックデータ50件程度 | **100万件想定** |
| インタースティシャルは15回ごと | **30回ごと** |
| **ダブルタップ**でリアクション | **単一タップ** |
| 長押し = お気に入り保存 | **長押し = BAD。**「保存」でも perfect でもない |
| リアクション最大5回・送りは手動 | **最大8回・8回到達で自動送り** |
| （フォントの指定なし → OS 任せ） | **フォント同梱で iOS/Android の見た目を揃える** |

一時的に「長押し = perfect 評価」「左スワイプ = BAD」という案があったが、
どちらも廃止。現在の割り当ては §3 が正。

また、リアクションがダブルタップだった前提で「単純タップは恒久的に未割り当て」
としていたが、リアクション自体が単一タップになったため**この制約は撤回**。

## 未確定

### 音（未定義・仕様の穴）
**現状、音は仕様にも実装にも一切存在しない。** 視覚と触覚だけで刺激を作っている。
ドパミン設計として刺激チャネルを1つ捨てている状態なので、
**無料の標準機能として入れる**方針（課金対象は視覚を主軸にする。
消音で使うユーザーが多く、音の価値が人により振れるため）。
リアクション8段・BAD の破壊音・切り替え音をどう作るかは未定。

### 演出カスタマイズ（検討中）
リワード広告で1日解放、課金で恒久解放という構成。
狙いは直接収益より**継続率**（このアプリには現在、戻る理由と進行感が無い）。
- 色パレットと演出パラメータは `theme.ts` のデータ差し替えだけで済むため実装コストほぼゼロ。
- **BAD の演出をカスタマイズする場合も無彩色の制約は守る**（§1 の色の意味づけ）。
- **入口が無いのが唯一の実コスト。** フィードは完全ボタンレスなので設定・ショップへの
  動線が存在しない。詳細画面をボタンレスの例外にした前例に寄せるのが自然。
- カタログは5〜8種程度に留める（選択肢自体がノイズになる）。
- これを継続率の柱にすると、アプリの性格が「純粋なフィード」から
  「フィード + 収集要素」に変わる。意図して選ぶべき変更。

詳細は MONETIZATION.md を参照。

### 1日の閲覧上限（方針: 採用。位置は実測で決める）
上限に到達したら「**動画を見て今すぐ続ける**」か「**待って回復**」かを選ばせる。
動画を選べばリワード収益（最高単価）、待つ方を選べば翌日戻る理由になり、
**どちらでも得**になる。ピッコマの「待てば無料」が広告なしで年間取引額1,000億円超を
成立させているのは、この待ち時間による習慣化が効いているため。

**上限の数値は決め打ちしない。** 同一ユーザーへの表示は増やすほど単価が落ちるので、
**限界の1件が生む広告収益がリワード1本の価値を下回る点**で切る。
メディエーションの impression-level revenue data で実測して決める。

注意すべき構造差: ピッコマが止めているのは「特定の次の1話」で牽引力があるが、
**雑学は交換可能で「これが見たい」が存在しない**。したがってゲートするのは
コンテンツではなく**連打中のフロー**（Candy Crush のライフ制と同型）。
止める位置が「熱中している最中」であることが条件。

詳細は MONETIZATION.md。

### その他

- **詳細説明のデータ設計。** 文字数の上限、本文と同じ生成パイプラインに乗せるか、
  個別ファイルの命名（100万件をどうディレクトリ分割するか）。
- **計測の受け口をどこに置くか。** 外部の分析サービスは使わないと決まったので、
  自前の受け口が必要（静的配信は GET だけなので、書き込み先は別途要る）。
- **設定・ショップ画面への動線。** フィードは完全ボタンレスなので入口が存在しない。
  演出カスタマイズを入れるなら必須。
- **年齢下限の具体値**（13歳 / 16歳 など）と、同意取得の扱い（GDPR / ATT）。
- **配信ホスティング。** GitHub Pages は容量と商用前提の観点で本番不可。
  Cloudflare R2 等を推奨。配信側は静的ファイルのみで完結させてあるので
  `src/config.ts` の差し替えで移れる。
